# Guide: การสรุปผลทดสอบ Prototype (Test Synthesis)
**โปรเจกต์:** Design Thinking — ผู้สูงอายุในสวนธนบุรีรมย์

ไฟล์นี้คือ **guide สำหรับ "กรอกข้อมูล"** ก่อนเข้าสู่ขั้นตอนสรุปผล — **ยังไม่ใช่ไฟล์สรุปผลสุดท้าย** ใช้บอกว่าคนที่รับผิดชอบ Version 1 หรือ Version 2 ต้องส่งมอบข้อมูลอะไรบ้าง เพื่อให้ทีมนำไปรวมกันตอบโจทย์ที่อาจารย์ต้องการ:

- Feedback Matrix from Test
- What to do next from Test feedback → Mode and issues to work on
- Explain what your next mode(s) should be based on user feedback

---

## 🧭 ภาพรวมขั้นตอน

| ขั้นตอน | ทำโดย | สถานะ |
| :--- | :--- | :--- |
| 1️⃣ รวบรวม & สังเคราะห์ข้อมูล (Synthesize) | รายคน (ตาม version ที่ดูแล) | ⬜ |
| 2️⃣ เปรียบเทียบ Version 1 vs Version 2 | รายคนกรอกฝั่งตัวเองลงไฟล์เดียวกัน | ⬜ |
| 3️⃣ สรุป Insight ใหม่ + ตัดสินใจทิศทาง | สรุปจากข้อมูลที่ส่งมอบไว้ (ไม่มีประชุม) | ⬜ |
| 4️⃣ ปรับปรุง Prototype (Refine) | รายคน (ตาม version ที่ดูแล) | ⬜ |

> ⚠️ แต่ละคนกรอกข้อมูลตาม Template ของ Step 1, 2, 4 ลงในไฟล์เดียวกัน (ดู 📁 โครงสร้างไฟล์ด้านล่าง) — ขั้นตอนที่ 3 จะสรุปจากข้อมูลที่ทุกคนส่งมอบไว้แล้วเท่านั้น ไม่ต้องนัดประชุม ห้ามข้ามไปสรุปทิศทางเลยโดยไม่มีข้อมูลดิบรองรับ

---

## 📁 โครงสร้างไฟล์ (File Structure)

ข้อมูลทั้งหมดของขั้นตอนนี้ (Step 1, 2, 3, 4 ของทั้ง Version 1 และ Version 2) ให้รวมอยู่ใน **ไฟล์เดียว** แทนการแยกไฟล์ต่อ version เหมือนตอน test-script/storytelling เพื่อให้ทุกคนเห็นข้อมูลทั้งหมดในที่เดียว และสรุปทิศทางได้โดยไม่ต้องนัดประชุม

```
DTproject/
└── test-synthesis.md      # ไฟล์เดียว รวมข้อมูลจากทั้ง 2 version + สรุปทิศทาง
```

โครงสร้างภายในไฟล์ `test-synthesis.md`:

```
# Test Synthesis
├── Version 1 (Fixed Board)
│   ├── 1. Synthesize (Raw Data / Affinity Mapping / Keep-Fix)
│   ├── 2. เปรียบเทียบ (มุมมองจาก Version 1)
│   └── 4. Refine (มุมมองจาก Version 1)
├── Version 2 (Mobile Board)
│   ├── 1. Synthesize (Raw Data / Affinity Mapping / Keep-Fix)
│   ├── 2. เปรียบเทียบ (มุมมองจาก Version 2)
│   └── 4. Refine (มุมมองจาก Version 2)
└── 3. Insight ใหม่ + ตัดสินใจทิศทาง (สรุปจากข้อมูลทั้งสองฝั่งด้านบน)
```

> คนรับผิดชอบ version ของตัวเอง กรอกเฉพาะส่วนของ version ตัวเองใน Step 1, 2, 4 ลงในไฟล์นี้ — ส่วน Step 3 จะถูกสรุปจากข้อมูลที่กรอกไว้แล้วทั้งหมด ไม่ต้องรอนัดประชุม

## 1️⃣ รวบรวมและสังเคราะห์ข้อมูล (Synthesize)
**คนรับผิดชอบ version ของตัวเอง ต้องส่งมอบ:**

### ✅ สิ่งที่ต้องทำ
- [ ] ดึง raw data จาก `test-script.md` ของ version ตัวเองมารวมในที่เดียว ได้แก่ คำตอบแบบ verbatim, hesitation point, assist count, และคะแนน wrap-up ทุกข้อ
- [ ] ทำ **Affinity Mapping** — จัดกลุ่ม feedback/ปัญหาที่คล้ายกันเป็นกลุ่มๆ (ใช้ pattern เดียวกับที่เคยทำใน `feedback.md` ตอนสรุป feedback presentation ครั้งที่ 2: **Feedback → Problem/Insight → Ideation → แนวทางที่เลือก**)
- [ ] แยกผลเป็น 2 กลุ่ม: **Keep** (ใช้งานได้ดี) และ **Fix** (จุดที่ติดขัด)

### 📋 Template (กรอกต่อ 1 version)

**Raw Data รวม**
| User | Verbatim เด่น | Hesitation Point | Assist Count | คะแนน Wrap-up |
| :--- | :--- | :--- | :--- | :--- |
| ผู้ทดสอบ 1 | "..." | ... | ... | ... |
| ผู้ทดสอบ 2 | "..." | ... | ... | ... |

**Affinity Mapping**
| กลุ่ม Feedback | ตัวอย่างคำพูด/พฤติกรรมที่เจอ | จำนวนคนที่พูดถึง |
| :--- | :--- | :--- |
| เช่น "หาโซนไม่เจอ" | ... | ... |
| เช่น "กลัวโดนหลอก" | ... | ... |

**สรุป Keep vs Fix**
| ✅ Keep (ใช้งานได้ดี) | ⚠️ Fix (ต้องปรับปรุง) |
| :--- | :--- |
| ... | ... |

## 2️⃣ เปรียบเทียบ Version 1 vs Version 2
**คนรับผิดชอบแต่ละ version สรุปฝั่งตัวเองมาก่อน ทีมค่อยนำมาเทียบกัน**

### ✅ สิ่งที่ต้องทำ (ฝั่งตัวเอง)
- [ ] สรุปว่า version ที่ตัวเองดูแล ตอบโจทย์ **persona ไหนได้ดีกว่า** จากพฤติกรรม/คำพูดจริงของ user ตอน test (ห้ามเดาเอง)
- [ ] ระบุ **ข้อดี-ข้อเสีย** ของลักษณะบอร์ด (ยึดติด vs เคลื่อนที่ได้) จากสิ่งที่ user สะท้อนจริง ไม่ใช่สมมติฐานตอน ideate

### 📋 Template (กรอกต่อ 1 version)

| หัวข้อ | รายละเอียด |
| :--- | :--- |
| Version ที่ดูแล | Version 1 / Version 2 |
| ตอบโจทย์ Persona ไหนดีที่สุด | ... (พร้อมเหตุผลจากคำพูด/พฤติกรรมจริง) |
| ข้อดีที่ user พูดถึงจริง | ... |
| ข้อเสีย/ปัญหาที่ user เจอจริง | ... |

> 💡 เมื่อทั้งสองฝั่งกรอกเสร็จ ทีมจะนำมาวางคู่กันเพื่อเทียบตรงๆ ว่าแบบไหนตอบโจทย์อะไรได้ดีกว่ากัน

---

## 3️⃣ สรุปเป็น Insight ใหม่ + ตัดสินใจทิศทาง
**ไม่มีการประชุม — ให้ส่งมอบข้อมูลลงในไฟล์แทน แล้วสรุปจากข้อมูลที่กรอกไว้**

### ✅ สิ่งที่ต้องส่งมอบ (แต่ละคน)
- [ ] กรอกผลจาก Step 1-2 ของ version ตัวเองลงในไฟล์ `test-synthesis.md` ให้ครบก่อน
- [ ] ถ้ามีปัญหาใหญ่โผล่มาระหว่าง test (เช่น ความกังวลเรื่อง scammer ที่เคยเจอมาก่อน) ให้สรุปในไฟล์ว่า **solution ที่ใส่ไปแล้ว** (เช่น กฎห้ามระบุเบอร์โทร/ที่อยู่) **แก้ปัญหานั้นได้จริงไหม** จากสิ่งที่สังเกตตอน test จริง (user พูดถึงกฎนี้ไหม รู้สึกมั่นใจขึ้นไหม)

### 🎯 สิ่งที่ต้องสรุปจากข้อมูลที่ส่งมอบ (รวมจากทั้งสองฝั่ง)
- [ ] สรุปว่าจะเลือก Version ไหนไปต่อ หรือจะ **รวมจุดเด่นของทั้งสองแบบ** เป็น concept เดียว โดยอ้างอิงจากข้อมูลที่ทุกคนกรอกไว้ในไฟล์เท่านั้น
- [ ] สรุป Insight ใหม่ที่ได้จากการ test (ต่างจาก insight เดิมตอน define/ideate อย่างไร)

### 📋 Template

| หัวข้อ | สรุป |
| :--- | :--- |
| Insight ใหม่จากการ test | ... |
| ปัญหาเดิมที่ตรวจสอบซ้ำ (เช่น scammer) | แก้ได้จริงไหม: ... / หลักฐานจาก test: ... |
| ทิศทางที่เลือก | Version 1 / Version 2 / รวมสองแบบ |
| เหตุผล | ... |

## 4️⃣ ปรับปรุง Prototype (Refine)
**คนรับผิดชอบ version ของตัวเอง ต้องส่งมอบ:**

### ✅ สิ่งที่ต้องทำ
- [ ] ระบุจุดที่ user สับสนหรือต้องความช่วยเหลือบ่อยที่สุด (อ้างอิงจาก Step 1) พร้อมแนวทางแก้
- [ ] ถ้ามีเวลา: ทำ prototype เวอร์ชันถัดไป (v1.1 หรือ v2.1) แล้ว test ซ้ำรอบสั้นๆ กับ user กลุ่มเดิมหรือกลุ่มใหม่

### 📋 Template

| จุดที่ต้องแก้ | สาเหตุ (จากข้อมูล test) | แนวทางแก้ใน v1.1 / v2.1 |
| :--- | :--- | :--- |
| ... | ... | ... |

## 📝 หมายเหตุ

- ไฟล์นี้เป็น guide สำหรับ "กรอกข้อมูล" เท่านั้น ตัวข้อมูลจริงให้กรอกลงใน `test-synthesis.md` (ไฟล์เดียว รวมทุก version) เพื่อตอบโจทย์อาจารย์ 3 ข้อ: Feedback Matrix, Mode ถัดไปที่จะทำ, และเหตุผลที่เลือก mode นั้นจาก feedback จริง
- ทุก Insight/ข้อสรุปต้องอ้างอิงจากคำพูด/พฤติกรรมจริงของ user ตอน test เท่านั้น ไม่ใช่ความเห็นส่วนตัวของทีม
